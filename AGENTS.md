It scopes every request to the authenticated session user, maps remote rows back to local domain types, archives by default for deletes, keeps AI enrichment separate, and handles URL/tag duplicate conflicts where possible.
- **M7 scaffold** — sync service: `src/sync/sync-bookmarks.ts` uploads queue entries through `createBookmark` (idempotent server-side, so retries cannot duplicate remote rows); the local bookmark row adopts the remote ID via `repository.replaceBookmark`. The store auto-syncs when auth and local data are ready or a new pending entry appears; failed entries record retry count/last error and are retried on the next save or the manual "Sync now" action in Settings, which also shows live sync status.
- **M8 scaffold** — share intake via `expo-share-intent@7` (SDK 56). The `expo-share-intent` config plugin is registered in `app.json` (default text/URL filters; uses the existing `stash` scheme). `src/share/share-intent-handler.tsx` consumes `useShareIntentContext`, extracts a URL from the shared payload (`extractFirstUrl` in `domain/urls.ts` handles text that wraps a link), saves it via the existing `addBookmark` (persist-then-queue, never blocks on network), and shows a short non-blocking toast — no full editor. `ShareIntentProvider` wraps the root layout. The native module is a no-op on web. **Post-capture landing**: the OS share flow always foregrounds the host app, but a toast-mode share must never strand the user on the *stale* Detail/Settings screen the app happened to resume onto (a warm start keeps the last in-memory screen). So toast mode now (a) awaits the durable write — `addBookmark` returns a `persisted` promise so a capture is never lost to backgrounding mid-write — then (b) dismisses Stash entirely on Android via `dismissAfterShare` (`src/share/dismiss.ts`: `ToastAndroid` confirmation + `BackHandler.exitApp()`, returning the user to the app they shared from), or where the OS can't self-dismiss (iOS/web) lands on the Inbox. Inbox mode still jumps to the Inbox to surface the saved item. The native dismissal needs on-device verification (see "Remaining verification").
- **M9** — metadata enrichment placeholder. `src/domain/enrichment.ts` derives title/site_name/favicon_url from the URL (no network, deterministic; a real OpenGraph fetch drops into `deriveMetadata` later). The store runs `enrichInBackground` after each save and over any still-`pending` bookmarks on startup: it is fire-and-forget (capture never blocks), only fills generated fields that are still null (user-typed titles are preserved), and records a `failed`/`skipped` status on error or text-only shares instead of throwing — so enrichment can never break bookmark creation. `metadata_status` transitions pending → complete/failed/skipped. The Detail screen renders the favicon and preview image when present.
- **M10** — MVP polish + release readiness. Archive/unarchive and permanent delete on the Detail screen (store `archiveBookmark`/`deleteBookmark`; repository gained `deleteBookmark`/`removeQueueEntry`; deleting also drops the pending queue entry so it never syncs). Inbox shows loading/empty/error states (`loadError` surfaces a storage-failure banner). Settings shows library counts and app version. Explicit bundle IDs (`com.stash.app`) in `app.json`; `apps/mobile/eas.json` defines development/preview/production build profiles; `docs/development/releasing.md` documents the build/release flow and an internal-build smoke-test checklist.

- **Local-first tags** — `addTagsToBookmark`/`removeTagFromBookmark`/`acceptSuggestedTags` are now optimistic + queued (like collection assignment), so tagging a synced bookmark works instantly and offline instead of blocking on a network round-trip. Pure engine in `src/domain/pending-tags.ts` (applyTagOp / applyPendingTagOps / enqueueTagOp with add↔remove cancellation / reconcileSyncedAdd, all unit-tested): an add creates an optimistic `local-tag-<slug>` tag+link; the op is persisted in the `pending_tag_ops` meta queue. `syncTagOps` (run from `syncNow` and right after each edit when online) uploads via `api.addTags`/`removeTags`, swaps the local tag id for the server's, and dequeues; failures stay queued. - **Account-switch data-loss guard** — pull-sync used to delete local bookmarks that were synced under a *different* account (e.g. signing into a fresh Google account when manual linking is off made the pull treat the anonymous user's rows as "deleted remotely" and wipe them locally; the cloud rows survived). Now `src/sync/account-transition.ts` (pure, tested) plans the transition: anonymous→real **carries over** (re-home rows as local pending creates), real A→real B **replaces** (drop A's cache; safe in A's cloud), same/first user is a no-op. `pullRemoteChanges` tracks `synced_user_id`/`synced_user_is_anonymous` in meta, **skips the deletion diff and resets the watermark on a user change**, and logs switches/deletions to the in-app buffer. The lossless path remains Supabase identity linking (same user_id). See `docs/architecture/sync-account-switching.md`.
- **Sign-in pull trigger (reinstall data restore)** — the store now pulls whenever the signed-in *user id* changes, not just once per launch. The startup pull was guarded by a one-shot `initialPullDone` ref (so it fired for the auto-created anonymous user and never again), and the background-sync effect only fires when the queue has work — so signing in right after a reinstall (empty queue) triggered no pull and the account's cloud data only reappeared after a cold start. The effect now keys off `auth.userId` (`lastSyncedUserId` ref), so the anonymous→real upgrade at sign-in and any account switch immediately run `syncNow` (account-transition + pull). See `src/__tests__/sign-in-pull.test.tsx`.

Implemented as a hand-rolled browser-based PKCE flow (no `supabase-js`): pure helpers in `src/supabase/oauth.ts` (base64url, authorize-URL builder, redirect parser; unit-tested under the Node lane), runtime orchestration in `src/supabase/run-oauth.ts` (the only auth file importing native modules — `expo-web-browser`, `expo-crypto`, `expo-linking`), and network methods on `StashSupabaseClient` (`requestOAuthLinkUrl`, `exchangeCodeForSession`, `signOut`). The auth provider gained an `'authenticated'` status plus `isSignedIn`/`email`/`signIn`/`signOut`; when a session exists the anonymous user is linked in place (token passed to `/authorize`) so bookmarks carry over, falling back to a plain sign-in if manual linking is off. Dashboard setup + limitations (real provider creds needed to test end-to-end; native Apple button is a submission-time follow-up) are in `docs/development/setup.md`.

Reviewed state persists across "Refresh AI suggestions" by name (a genuinely new suggestion still shows). See the regression tests in `src/__tests__/ai-enrichment-store.test.tsx` ("the badge stays gone after accepting then removing a suggested tag") and `src/domain/ai-suggestions.test.ts`.
  - **"Dismiss all" + manual re-run reconsiders** — the Detail suggestion row shows a one-tap **"Dismiss all"** (`TagField` `onDismissAllSuggestions`, rendered only when there's more than one suggestion); it marks every AI suggestion reviewed at once (hashtag chips stay session-local, like the single dismiss). A **manual** "Suggest with AI" tap calls `clearReviewedSuggestions(bookmarkId)` before re-enriching, so previously-dismissed tags the model still recommends can re-surface; background sync never clears reviewed state. See the "dismiss all clears every suggestion" (`bookmark-detail-screen`) and "clearReviewedSuggestions forgets dismissals" (`ai-enrichment-store`) tests.

All four are pure (no React/native) so the Node lane tests them (`locale.test.ts`, `translate.test.ts`, incl. a guard that every `ko` key exists in `en`). `index.tsx` is the only i18n file importing a native module (`expo-localization`): `I18nProvider` reads the device locale **synchronously** at first render (so capture is never blocked) and loads the stored override (`pref.locale` in the repository meta store, mirroring `share-behavior`) in the background; `useI18n()`/`useT()` expose `t`, the resolved `locale`, `preference`, `setLocalePreference`, and locale-aware `formatDate`/`formatNumber`. Device locale follows the system with English fallback; the brand name "Stash" is intentionally never translated. - **M12 — locale-aware AI output + visible degraded mode** — closes out 0.2.0. **Locale-aware:** the `ai-enrich` request now carries the user's active `locale`; the store reads it from `useI18n()` (via a ref so `requestAiEnrichment` stays stable) and `requestEnrichment(id, metadata, locale)` forwards it. - **Browse-facet icon vocabulary (issue #142)** — the Inbox browse shelf used to render the `No collection` facet as bare text wedged between bare collection-name chips and `#tag` chips, so its meaning read as ambiguous ("isn't '컬렉션 없음' the same as 'no tag'?"). - **No-link shares saved as text notes** — KakaoTalk (and similar apps) often share plain text with no URL. The share path used to drop these with a "No link found to stash" toast. The data model already anticipated text-only items (`Bookmark.url: string | null`, `content_type: 'text'`, `CreateBookmarkInput.shared_text`) and the cloud API/sync/export all round-tripped them — only the local capture path didn't. Now `addBookmark` accepts `shared_text` (no URL): it creates a `content_type:'text'` note with `url:null`/`url_hash:null`, stores the shared text in `description` (mirroring the cloud API's `shared_text → description` mapping so a pulled-back note matches the locally captured one), queues a create with `shared_text`, and runs the existing enrichment path (which marks `metadata_status:'skipped'` for a URL-less row). **No dedupe** for text notes — they have no canonical key and re-sharing the same message is plausibly intentional, so each share is its own note. `ShareIntentHandler` carries the raw `shareIntent.text` and, when there's no URL, saves it as a note (`addBookmark({ shared_text })`); a genuinely empty share still gets the "nothing to save" toast (`addBookmark` returns `invalid`). A new pure `src/domain/item-display.ts` `displayTitle(bookmark)` (title → url → description, else null) lets lists/headers render a note's text as its label; wired into Inbox (card/list/menu), Archived, Review, and Detail (which also suppresses the redundant Description row when it equals the header title). AI enrichment still works for synced notes (it already sends description/notes/content_type). Tests: `src/domain/item-display.test.ts` and two new `share-intent-handler.test.tsx` cases (no-link text → note; empty share → no save).

## Building an installable Android APK (no EAS account)

The fastest way to get a real, installable APK is the **`.github/workflows/android-apk.yml`** GitHub Actions workflow. It runs `expo prebuild` → Gradle `assembleRelease`, signs with the debug keystore, and **publishes a standalone APK as a GitHub Release with an install QR code** — no EAS/Expo account needed. (EAS via `eas.json` is still the path for store builds; see `docs/development/releasing.md`.)

**How the trigger maps to output** (`workflow_dispatch` input `version`, or a pushed git tag) — every build now publishes a Release with the raw `.apk` + QR (and still uploads a `stash-android-apk` run artifact):

- `version` **blank** or a **hyphenated** pre-release tag (e.g. `v0.1.7-rc8`) → refreshes the single rolling **`dev`** prerelease in place (stable `dev` tag, `stash-dev-android.apk`). Use this for test builds.
- A clean `vX.Y.Z` (no hyphen), as the input or a pushed `vX.Y.Z` git tag → publishes a **versioned** prerelease, kept forever.

**From a Claude Code web session (GitHub MCP tools):**

1. `actions_run_trigger` (method `run_workflow`) → `workflow_id: "android-apk.yml"`, `ref: "main"`, `inputs: { version: "v0.1.7-rc8" }`.
2. `actions_list` (`list_workflow_runs`, filter `event=workflow_dispatch`) → grab the newest run's `id`.
3. Poll `actions_get` until `status: "completed"` (~6–7 min; arm64-v8a only). Don't `sleep`-poll — arm a short background timer between checks.
4. `get_latest_release` / `get_release_by_tag` (tag `dev` for test builds) → share the Release URL. The user opens it on their phone, scans the QR (or taps the download link), and installs the `.apk` directly — no artifact unzip. (The Release only appears once the build succeeds.)

**With the `gh` CLI** (non-MCP shells):

```bash
gh workflow run android-apk.yml -f version=v0.1.7-rc8 --ref main
gh run list --workflow android-apk.yml -L 1     # find the run id
gh run watch <run-id>                            # wait for it
gh run download <run-id> -n stash-android-apk    # downloads the .apk
```

Notes: the build is **arm64-v8a only** (every modern phone) to stay fast/small; the APK is debug-signed but fully standalone (installs + runs on its own). If the repo's `EXPO_PUBLIC_SUPABASE_*` secrets are set, cloud sync is baked in; otherwise it's a local-only build. The app self-reports its build commit in Settings (via `EXPO_PUBLIC_GIT_SHA`), so you can confirm which commit an installed APK came from.

## Environment gotchas (sandboxed/cloud sessions)

- `expo install <pkg>` may fail offline against the Expo versions API. Get the SDK-pinned version locally instead: `node -e "console.log(require('./apps/mobile/node_modules/expo/bundledNativeModules.json')['<pkg>'])"`, then `pnpm add <pkg>@<that version>`.
- `pnpm install` reports two benign peer-dependency warnings (react-native-worklets, @react-native/metro-config).

## Known minor gaps

- Duplicate detection only checks in-memory state; a save made while the startup load is in flight could miss a stored duplicate (cosmetic: creates a second entry rather than losing data). The share path — the worst offender, since a share cold-starts the app right when the store is still loading — now copies the shared URL into local state and releases the OS intent immediately, then defers the actual `addBookmark` until the store has loaded (`ShareIntentHandler`). So re-sharing an already-stashed URL dedupes instead of piling up duplicates stuck at "sync pending", while a `resetOnBackground`/back-out during a slow SQLite load can't drop the capture (capture stays sacred). The manual Add screen can still hit the dedupe window in theory, but it's only reachable after the app is already open. See `src/__tests__/share-intent-handler.test.tsx`.
- `bookmarks` SQLite table stores the full record as a JSON column plus `created_at`/`is_archived` columns; promote fields to real columns when query needs grow.
- **Cloud `url_hash` is now canonical.** `api/bookmarks.ts` `createBookmark` stores `url_hash = canonicalizeUrl(url)` (was the raw normalized URL), matching the client and the active-URL unique index — so `…?utm_source=x` and the bare URL no longer become two cloud rows. Rows created before this fix keep their old non-canonical `url_hash`; run the one-off `pnpm dedupe:supabase` (dry-run by default, `--apply` to execute; needs `SUPABASE_SERVICE_ROLE_KEY`) to merge any existing duplicates and rewrite stale hashes. Planner is pure/tested in `src/domain/dedupe.ts` (`planBookmarkDeduplication`); the script (`scripts/dedupe-bookmarks.mjs`) folds each duplicate's tags + AI enrichments into the earliest row before deleting it.
