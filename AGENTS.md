## Post-MVP work completed

- **Test runner** — two lanes. `pnpm test`: Node 22's built-in runner (`--experimental-transform-types` + the `@/` alias resolver in `scripts/alias-loader.mjs`, preloaded via `--import`) over `src/**/*.test.ts` for pure logic (URL handling, enrichment, page-metadata parser, sync/pull engines; fake API/repository). `pnpm test:components`: jest-expo + @testing-library/react-native over `src/**/*.test.tsx` for hooks/components (store behavior via `renderHook`, Inbox rendering/search) with an in-memory repository fake (`src/__tests__/helpers/fake-repository.ts`); component tests live in `src/__tests__/` so expo-router never sees them as routes. RNTL v14 note: `render`/`renderHook`/`fireEvent` are async — await them, and use `await act(async () => …)` for state updates.
- **CI** — `.github/workflows/ci.yml` runs lint, typecheck, and tests on pushes to main and on every PR.
- **Mutation sync** — queue entries carry an `operation` (`create`/`update`/`delete`). Archiving/editing/collection-assigning a synced bookmark enqueues an `update` (the sync service re-sends the LATEST user-editable fields **plus generated metadata** — site_name/favicon_url/preview_image_url/metadata_status — so on-device enrichment reaches the cloud; last write wins); deleting one enqueues a durable `delete` (permanent remote removal, survives restart). Completing enrichment for a synced bookmark also enqueues such an update. One queue entry per bookmark: newer mutations supersede older ones. A bookmark archived while its create was uploading gets reconciled with a follow-up update. SQLite migration: `ALTER TABLE ... ADD COLUMN operation` guarded by try/catch for pre-existing databases.
- **Real OpenGraph fetch** — `src/domain/page-metadata.ts` fetches a page (AbortController timeout, HTML-only, size-capped) and parses og:/twitter: meta, `<title>`, and favicon links; `enrichBookmark` prefers fetched values and falls back to URL-derived ones, with the fetcher injectable for offline tests.
- **Archived view** — `/archived` lists archived bookmarks (restorable via detail's Unarchive); reachable from Settings' Library row.
- **Pull sync** — `src/sync/pull-bookmarks.ts` implements `docs/design/ux-spec.md` §9: upload-then-pull on startup and "Sync now"; incremental by `updated_at` watermark (5-minute overlap for clock skew, stored in the repository meta store); last-write-wins except rows with queued local work; remote deletions via ID-list diff; AI enrichments cached durably (new `enrichments` table / storage key) and read by Detail in place of mock data. Settings shows the last pull time.
- **Tags & collections** (ux-spec §10) — each pull also replaces a local snapshot of tags/links/collections (`repository.listTagData`/`replaceTagData`). Detail has a tag editor (add/remove via `api.addTags`/`removeTags`, online + synced bookmarks only) and a collection chip picker (local-first via the existing update mutation; `api.createCollection` for new ones).
- **Search & editing** (ux-spec §11) — Inbox search (`src/domain/search.ts`, AND-of-terms over title/description/notes/URL) and inline title/notes editing on Detail via `updateBookmarkFields`, which shares the local-first `applyBookmarkUpdate` path with archive and collection assignment.
- **Branding** (ux-spec §12) — generated Stash icon set (bookmark ribbon on #208AEF): main icon, Android adaptive fg/bg/monochrome, splash glyph, favicon. iOS uses the standard `icon.png` (the template's liquid-glass `expo.icon` dir was removed).
- **Local-first tags** — `addTagsToBookmark`/`removeTagFromBookmark`/`acceptSuggestedTags` are now optimistic + queued (like collection assignment), so tagging a synced bookmark works instantly and offline instead of blocking on a network round-trip. Pure engine in `src/domain/pending-tags.ts` (applyTagOp / applyPendingTagOps / enqueueTagOp with add↔remove cancellation / reconcileSyncedAdd, all unit-tested): an add creates an optimistic `local-tag-<slug>` tag+link; the op is persisted in the `pending_tag_ops` meta queue. `syncTagOps` (run from `syncNow` and right after each edit when online) uploads via `api.addTags`/`removeTags`, swaps the local tag id for the server's, and dequeues; failures stay queued. Pull re-layers unsynced ops over the fresh server snapshot (`applyPendingTagOps`) so optimistic tags survive the wholesale replace. Still gated on the bookmark having a remote identity (a brand-new, not-yet-synced bookmark can't be tagged until its create syncs). See `src/__tests__/local-first-tags.test.tsx`.
- **Account-switch data-loss guard** — pull-sync used to delete local bookmarks that were synced under a *different* account (e.g. signing into a fresh Google account when manual linking is off made the pull treat the anonymous user's rows as "deleted remotely" and wipe them locally; the cloud rows survived). Now `src/sync/account-transition.ts` (pure, tested) plans the transition: anonymous→real **carries over** (re-home rows as local pending creates), real A→real B **replaces** (drop A's cache; safe in A's cloud), same/first user is a no-op. `pullRemoteChanges` tracks `synced_user_id`/`synced_user_is_anonymous` in meta, **skips the deletion diff and resets the watermark on a user change**, and logs switches/deletions to the in-app buffer. The lossless path remains Supabase identity linking (same user_id). See `docs/architecture/sync-account-switching.md`.
- **Sign-in pull trigger (reinstall data restore)** — the store now pulls whenever the signed-in *user id* changes, not just once per launch. The startup pull was guarded by a one-shot `initialPullDone` ref (so it fired for the auto-created anonymous user and never again), and the background-sync effect only fires when the queue has work — so signing in right after a reinstall (empty queue) triggered no pull and the account's cloud data only reappeared after a cold start. The effect now keys off `auth.userId` (`lastSyncedUserId` ref), so the anonymous→real upgrade at sign-in and any account switch immediately run `syncNow` (account-transition + pull). See `src/__tests__/sign-in-pull.test.tsx`.
- **OAuth login (Apple/Google)** — anonymous-first accounts can be upgraded to a permanent account from Settings. Implemented as a hand-rolled browser-based PKCE flow (no `supabase-js`): pure helpers in `src/supabase/oauth.ts` (base64url, authorize-URL builder, redirect parser; unit-tested under the Node lane), runtime orchestration in `src/supabase/run-oauth.ts` (the only auth file importing native modules — `expo-web-browser`, `expo-crypto`, `expo-linking`), and network methods on `StashSupabaseClient` (`requestOAuthLinkUrl`, `exchangeCodeForSession`, `signOut`). The auth provider gained an `'authenticated'` status plus `isSignedIn`/`email`/`signIn`/`signOut`; when a session exists the anonymous user is linked in place (token passed to `/authorize`) so bookmarks carry over, falling back to a plain sign-in if manual linking is off. Sync now keys off `auth.session`/`isSignedIn` rather than the `anonymous` status so authenticated users keep syncing. Redirect URI is `stash://auth/callback`. Dashboard setup + limitations (real provider creds needed to test end-to-end; native Apple button is a submission-time follow-up) are in `docs/development/setup.md`.

- **Auto-report handled errors to Sentry** — crash & error monitoring (`src/observability/`) already auto-captures *unhandled* errors via `Sentry.wrap` + native crash handling, but this app deliberately swallows and `console.error`s many handled failures (enrichment/sync, the storage banner) so capture is never broken — those never reached Sentry. `log-buffer.ts` now exposes `onConsoleEntry(listener)` and notifies it from `recordLog` itself (raw args passed through from the console wrapper so the original Error/stack survives), so **both** `console.error(...)` and direct `recordLog('error', …)` calls reach the bridge — e.g. the native SQLite-open failure in `storage/repository.native.ts`, which only `recordLog`s. `sentry.ts` subscribes on init: error-level entries are forwarded as a `Sentry.captureException`, with a re-entrancy guard so the SDK's own logging can't loop. Privacy-first per `docs/api/bookmarks.md`: the pure, Node-tested `sentry-report.ts` scrubs URLs and emails from both the message and the stack before anything leaves the device (bookmark URLs are user content). Still a no-op until `EXPO_PUBLIC_SENTRY_DSN` is set. See `src/observability/sentry-report.test.ts` and the listener test in `log-buffer.test.ts`. `pnpm verify:sentry` (`scripts/verify-sentry.mjs`, mirroring `verify:supabase`) is an end-to-end smoke test: it parses the DSN via `parseSentryDsn` and POSTs a synthetic `environment:verify` event to the ingest API, asserting it is accepted — proving the DSN→project pipeline without a device build.

## Building an installable Android APK (no EAS account)

The fastest way to get a real, installable APK is the **`.github/workflows/android-apk.yml`** GitHub Actions workflow. It runs `expo prebuild` → Gradle `assembleRelease`, signs with the debug keystore, and **publishes a standalone APK as a GitHub Release with an install QR code** — no EAS/Expo account needed. (EAS via `eas.json` is still the path for store builds; see `docs/development/releasing.md`.)

**How the trigger maps to output** (`workflow_dispatch` input `version`, or a pushed git tag) — every build now publishes a Release with the raw `.apk` + QR (and still uploads a `stash-android-apk` run artifact):

- `version` **blank** or a **hyphenated** pre-release tag (e.g. `v0.1.7-rc8`) → refreshes the single rolling **`dev`** prerelease in place (stable `dev` tag, `stash-dev-android.apk`). Use this for test builds.
- A clean `vX.Y.Z` (no hyphen), as the input or a pushed `vX.Y.Z` git tag → publishes a **versioned** prerelease, kept forever.

**From a Claude Code web session (GitHub MCP tools):**

1. `actions_run_trigger` (method `run_workflow`) → `workflow_id: "android-apk.yml"`, `ref: "main"`, `inputs: { version: "v0.1.7-rc8" }`.
2. `actions_list` (`list_workflow_runs`, filter `event=workflow_dispatch`) → grab the newest run's `id`.
3. Poll `actions_get` until `status: "completed"` (~6–7 min; arm64-v8a only). Don't `sleep`-poll — arm a short background timer between checks.
4. `get_latest_release` / `get_release_by_tag` (tag `dev` for test builds) → share the Release URL. The user opens it on their phone, scans the QR (or taps the download link), and installs the `.apk` directly — no artifact unzip. (The Release only appears once the build succeeds.)

**With the `gh` CLI** (non-MCP shells):

```bash
gh workflow run android-apk.yml -f version=v0.1.7-rc8 --ref main
gh run list --workflow android-apk.yml -L 1     # find the run id
gh run watch <run-id>                            # wait for it
gh run download <run-id> -n stash-android-apk    # downloads the .apk
```

Notes: the build is **arm64-v8a only** (every modern phone) to stay fast/small; the APK is debug-signed but fully standalone (installs + runs on its own). If the repo's `EXPO_PUBLIC_SUPABASE_*` secrets are set, cloud sync is baked in; otherwise it's a local-only build. The app self-reports its build commit in Settings (via `EXPO_PUBLIC_GIT_SHA`), so you can confirm which commit an installed APK came from.

## Known minor gaps

- Duplicate detection only checks in-memory state; a save made while the startup load is in flight could miss a stored duplicate (cosmetic: creates a second entry rather than losing data). The share path — the worst offender, since a share cold-starts the app right when the store is still loading — now copies the shared URL into local state and releases the OS intent immediately, then defers the actual `addBookmark` until the store has loaded (`ShareIntentHandler`). So re-sharing an already-stashed URL dedupes instead of piling up duplicates stuck at "sync pending", while a `resetOnBackground`/back-out during a slow SQLite load can't drop the capture (capture stays sacred). The manual Add screen can still hit the dedupe window in theory, but it's only reachable after the app is already open. See `src/__tests__/share-intent-handler.test.tsx`.
- **Durable share capture (fixes "shared but the item wasn't added").** Holding the captured URL only in React state until the deferred save is *not* durable across a process death — and Android backgrounds Stash the instant a share is handled in the default toast mode (the share sheet returns to the source app), so the OS can suspend/kill the process before the deferred `addBookmark` ever lands, and the shared item silently never appears. `ShareIntentHandler` now also calls `recordPendingShare` the moment it captures, persisting the normalized URL to a durable `pending_shares` meta queue (pure helpers + types in `src/domain/pending-shares.ts`). On the next launch the store drains any leftover and saves it. No double-save: each record is tagged with a per-launch `session_id` (`SHARE_SESSION_ID`), and the recovery drain (runs once, after load) only re-saves shares from a *different* launch — a share the current launch still owns is saved by the handler itself and clears its own record via `addBookmark` (gated by an in-memory `handlingShares` set so manual adds/imports don't pay a meta write). Session-id rather than live-ownership tracking is required because the handler (a child) clears its record before the provider's drain effect (the parent) runs. See the recovery/durability cases in `src/__tests__/share-intent-handler.test.tsx` and `src/domain/pending-shares.test.ts`.
- `bookmarks` SQLite table stores the full record as a JSON column plus `created_at`/`is_archived` columns; promote fields to real columns when query needs grow.
- **Cloud `url_hash` is now canonical.** `api/bookmarks.ts` `createBookmark` stores `url_hash = canonicalizeUrl(url)` (was the raw normalized URL), matching the client and the active-URL unique index — so `…?utm_source=x` and the bare URL no longer become two cloud rows. Rows created before this fix keep their old non-canonical `url_hash`; run the one-off `pnpm dedupe:supabase` (dry-run by default, `--apply` to execute; needs `SUPABASE_SERVICE_ROLE_KEY`) to merge any existing duplicates and rewrite stale hashes. Planner is pure/tested in `src/domain/dedupe.ts` (`planBookmarkDeduplication`); the script (`scripts/dedupe-bookmarks.mjs`) folds each duplicate's tags + AI enrichments into the earliest row before deleting it.
